- **enkryptai-stack, platform-stack:** keyless AWS red team targets on EKS. One value, `global.redteam.awsRoleArn`, sets the IRSA annotation on the `redteam-workflow` service account (platform-stack) and the `redteam-proxy` service account (enkryptai-stack), and the dashboard's `ENKRYPT_REDTEAM_AWS_ROLE_ARN`. Give both releases the same value with one shared values file ([docs/keyless-target-auth.md](docs/keyless-target-auth.md)). Empty changes nothing. EKS only until AKS support is decided. With the value set, the red team pods run as that role, which can only assume roles: a Bedrock target with neither keys nor a role, which used the node's identity before, now fails. Give such targets a role before you set the value.
- **enkryptai-stack:** `redteam-proxy` runs as its own service account, `redteam-proxy`, not the namespace's `default` account. On upgrade, move anything you added to `default` for the proxy (an IRSA annotation, for example) to `redteam-proxy`. `redteam-proxy.configMap.TARGET_AUTH_SINGLE_TENANT` defaults to `"true"`, so existing targets keep the pod's own AWS identity.
- **enkryptai-stack:** the `enkrypt-red-teaming` and `enkrypt-db-proxy` Kong plugins read `owner_assertion_private_key` and `owner_assertion_key_id` from `ENKRYPT_OWNER_ASSERTION_KEY` and `ENKRYPT_OWNER_ASSERTION_KEY_ID` in `gateway-env-secret`; the installer's secret generator creates both and sentry's `OWNER_ASSERTION_PUBLIC_KEYS`. Kong http-log no longer logs the `X-Enkrypt-Owner-Assertion` header. **Release order:** these plugin fields need a gateway image built from [enkryptai/enkryptai-apiaas#2272](https://github.com/enkryptai/enkryptai-apiaas/pull/2272). With an older gateway image, Kong's decK sync fails. Move `gateway-kong.image.gateway.tag` to that image in the same release.
